# 系統維護指南：日誌監控與服務重啟

本文件紀錄了如何監控 Sentiment Analysis 服務狀態、解讀 Gunicorn 日誌，以及執行服務重啟的標準作業程序。

## 1. 服務監控 (Real-time Monitoring)

我們已將 Gunicorn 設定為將日誌直接輸出至系統標準輸出，可透過 `journalctl` 即時查看所有請求與錯誤。

### 執行監控指令：

```bash
journalctl -u sentiment -f

```

### 日誌資訊解讀：

* **存取日誌 (Access Log)**：顯示每個請求的來源、時間、路徑與狀態碼。
> 範例：`"POST /analyze HTTP/1.1" 200` (200 代表成功，500 代表伺服器內部錯誤)


* **錯誤日誌 (Error Log)**：當應用程式發生例外時，會顯示完整的 **Traceback (錯誤堆疊)**。
> 當出現 `500` 錯誤時，請務必查看此處的 Python 錯誤路徑（檔案名稱與行號），這是定位 Bug 的最快方式。

## 2. 服務重啟與配置更新 (Restart Process)

當你修改了 Python 程式碼 (`main.py` 或 `src/analyzer.py`)，或者調整了 Systemd 設定檔，請依照下列步驟操作以確保變更生效。

### 第一步：修改 Systemd 設定檔 (若有調整參數)

若需要調整參數，請編輯設定檔：

```bash
sudo vi /etc/systemd/system/sentiment.service
```

### 第二步：重載設定並重啟服務

修改設定檔後，必須執行以下指令：

1. **重新載入 Systemd 設定**：
```bash
sudo systemctl daemon-reload
```


2. **重啟服務**：
```bash
sudo systemctl restart sentiment.service

```


3. **確認服務狀態**：
```bash
sudo systemctl status sentiment.service

```


*若狀態顯示 `active (running)`，即代表啟動成功。*

## 3. 常見問題排查邏輯

當系統發生異常（如前端報 500 錯誤）時，請依照此順序檢查：

1. **檢查服務是否存活**：使用 `systemctl status sentiment` 確認服務是否仍在 `active` 狀態。
2. **檢查即時日誌**：使用 `journalctl -u sentiment -f` 觀察是否出現 `CRITICAL: WORKER TIMEOUT` 或 `Exception`。
3. **確認請求是否過大/過慢**：
* 若有 `WORKER TIMEOUT`，請確認是否為模型處理文字過長導致超時。
* 可透過調整 Systemd 中的 `--timeout` 參數給予更多運算時間。


4. **檢查資源耗用**：觀察記憶體使用情況（日誌中會顯示 CPU 與記憶體峰值），避免因記憶體不足導致 Worker 被殺掉。
